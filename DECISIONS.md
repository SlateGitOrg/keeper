# Decisions

Rulings made while building keeper, in the order they came up. Each one says
what was decided, why, and what it costs if it turns out to be wrong.

## API

- Ruling: the API group is `backup.keeper.dev/v1alpha1` with three kinds (BackupPolicy, Backup, Restore), and object storage is configured inline in each spec instead of through a fourth "BackupStorageLocation" kind. — The spec asked for these three CRDs. Inline config keeps every Backup self-describing, and that spec is also what gets written into the backup manifest. — If it's wrong: many policies repeat the same endpoint/bucket/secret. Adding a location kind later means a v1alpha2 and a conversion.
- Ruling: Backup and Restore specs are immutable (`self == oldSelf` CEL rule). — A Backup is a record of what was captured. Editing it after the fact would make status lie. — If it's wrong: users have to delete and recreate to fix a typo in a Backup that has not started yet.
- Ruling: all structural validation is done with CEL and OpenAPI rules, and there is no admission webhook. Cron syntax that passes the CEL shape check (5 fields or `@descriptor`) but fails the real parser shows up as `ScheduleValid=False`. — Webhooks need TLS and cert rotation, and they become an availability dependency. CEL cannot run a cron parser. — If it's wrong: `61 * * * *` is accepted at admission and only flagged in status.
- Ruling: `failedBackupsHistoryLimit` is a `*int32`. — With a plain int, an omitted field would serialise as `0` and the API server's default of 3 would never apply. That was found by the envtest validation test. — If it's wrong: nothing. It's just a pointer in the Go API.
- Ruling: `status.retention.kept` and `prunedTotal` are `omitempty`. — Merge-patching status from a Go zero value left the server object without required fields, which an envtest test exposed ("status.retention.kept: Required value"). — If it's wrong: nothing.

## Scheduling

- Ruling: use robfig/cron v3 (last release 2020) to parse schedules. — It's the parser the Kubernetes CronJob controller uses, so users get exactly CronJob syntax. — If it's wrong: we depend on an unmaintained library. Swapping it out only touches `internal/schedule`.
- Ruling: when several slots were missed, only the most recent one runs (CronJob semantics). Slots later than `startingDeadlineSeconds` are skipped and recorded. Suspending a policy does not advance `lastScheduleTime`. — This matches what operators already expect from CronJob. — If it's wrong: after an outage, no backup exists for the missed slots. That's acceptable for backups, because the newest data is what matters.
- Ruling: a missed-slot walk stops after 10,000 slots (`schedule.MaxMissed`). Beyond that it emits a warning and skips ahead to now. — This keeps a reconcile bounded, for example an every-minute schedule after a week of downtime. — If it's wrong: one warning, and no catch-up backup for that gap.
- Ruling: Backup names are `<policy>-<YYYYMMDDHHMM UTC slot>`, so `@every` must be at least 1m and policy names are capped at 50 characters (CEL). — Deterministic names make Backup creation idempotent: a retry after a lost status write finds the existing Backup instead of creating a duplicate. — If it's wrong: sub-minute schedules are impossible. Nobody needs those for volume backups.
- Ruling: a BackupPolicy does not own its Backups. They are linked by the `backup.keeper.dev/policy` label. — If they were owned, deleting a policy would garbage-collect every backup and its data, which is a dangerous default. — If it's wrong: deleting a policy leaves Backups behind and retention stops pruning them. Users delete them with a label selector.

## Retention

- Ruling: GFS semantics follow restic's `forget --keep-*`. Each rule keeps the newest backup from each of the N most recent periods that contain a backup. A backup is kept if any rule keeps it. Weeks are ISO weeks, and periods are computed in the policy's time zone. — The model is well known, it composes cleanly, and it has testable properties (idempotence, monotonicity). — If it's wrong: users who expect calendar-anchored windows ("everything from the last 7 days") will be surprised. See Limitations.
- Ruling: periods are tracked with a set of seen keys rather than "the key changed since the previous item". — In zones that fell back across midnight (e.g. America/Sao_Paulo before 2019), a calendar day shows up twice in a newest-first walk. The oracle property test covers this. — If it's wrong: nothing. It costs O(n) extra memory.
- Ruling: backups are bucketed by `status.snapshotTime`, falling back to creationTimestamp. — Retention should follow when the data is from, not when the object was created. — If it's wrong: nothing for scheduled backups, where the two are within seconds of each other.
- Ruling: pinned Backups (`backup.keeper.dev/pin=true`) are always kept and still occupy their periods. Failed Backups are pruned by count (`failedBackupsHistoryLimit`) and ordered by schedule slot. — Ordering by slot is needed because creationTimestamp has one-second resolution and tied in tests. — If it's wrong: a failed Backup whose post hook failed after a good copy is pruned like any other failed Backup.

## Drivers and data path

- Ruling: CSISnapshot keeps data inside the storage system (VolumeSnapshot objects). Only the backup manifest goes to object storage. — The spec's "snapshot via CSI ... to S3-compatible storage" is ambiguous. Exporting CSI snapshot contents needs a data mover per storage vendor. — If it's wrong: CSI backups don't survive loss of the storage system or cluster. FileCopy is the off-cluster option.
- Ruling: VolumeSnapshots have no owner reference. The Backup finalizer deletes them when `deletionPolicy: Delete`. — With an owner reference, `Retain` would be impossible, because GC would delete the snapshots. — If it's wrong: with the operator uninstalled, deleting Backups leaves snapshots behind.
- Ruling: FileCopy runs one Job per claim. The Job streams a gzip-compressed PAX tar through a SHA-256 hasher straight into a multipart upload. There's no deduplication and no incremental backups. — It's simple, it can be audited, and memory stays bounded at the part size. Restore verifies the hash before anything appears in the target. — If it's wrong: every backup is a full copy, so storage and transfer grow linearly with volume size times backup count.
- Ruling: one image serves as both manager and mover (`/keeper manager`, `/keeper mover`). The mover runs as root with every capability dropped except `DAC_OVERRIDE` (backup, read-only mount) or `CHOWN`/`DAC_OVERRIDE`/`FOWNER` (restore). — Those capabilities are on the Pod Security "baseline" allow-list. `DAC_READ_SEARCH`, the narrower choice, is not. — If it's wrong: namespaces that enforce "restricted" PSA reject mover pods.
- Ruling: the mover is pinned to the node of a running pod that mounts the claim (node affinity). — ReadWriteOnce volumes can be mounted by several pods on the same node, but not across nodes (multi-attach error). — If it's wrong: if the workload pod moves while the mover is pending, the mover may wait for a node that is draining.
- Ruling: restores extract into a staging directory inside the target volume, verify the archive SHA-256, and only then move entries into place. Entry paths are validated (no absolute paths, no `..`, never written through a symlink). setuid/setgid bits are stripped. — This way a corrupt or hostile archive leaves the target empty. — If it's wrong: a restore needs free space for the extracted data inside the target claim, which is the same space it ends up using anyway.
- Ruling: archives drop atime/ctime from PAX headers. — This makes archives of an unchanged tree byte-identical, which a test checks. — If it's wrong: those two timestamps are not restored. mtime is.

## Controller mechanics

- Ruling: hooks run inline in the Backup reconcile, with per-hook timeouts, and the number of Backup workers is bounded (`--max-concurrent-backups`). — A separate hook-runner mechanism would add a moving part without adding consistency. — If it's wrong: long hooks tie up workers. Other Backups wait.
- Ruling: hooks are at-least-once. Every reconciler reads its primary object from the API server (`APIReader`), not the cache, and writes status with optimistic locking. — With cached reads, a stale copy re-ran post hooks: the CSI test saw `fsfreeze -u` twice. One GET per reconcile is cheap at backup rates. — If it's wrong: if the operator crashes between running a hook and persisting status, the hook runs again, so hooks must be idempotent. This is documented.
- Ruling: a driver object that the cache has not seen yet (NotFound right after Start) is "pending", not "failed". Start re-creates objects that are truly missing. — Without this, informer lag failed Backups at random in early test runs. — If it's wrong: a Job that is deleted repeatedly keeps being recreated until its ActiveDeadline or the CSI timeout.
- Ruling: post hooks always run when pre hooks ran: after a pre-hook failure, after a snapshot failure, and when a Backup is deleted in any phase from PreHooks through PostHooks (fix round 1 widened this from Snapshotting only; see the ruling below). Pre hooks stop at the first Fail-policy failure. All post hooks run regardless. — Leaving an application frozen is worse than a failed backup. — If it's wrong: a post hook may run against an application whose pre hook never ran, so post hooks must tolerate that ("thaw" of an unfrozen filesystem).
- Ruling: deleting a Backup waits while a non-terminal Restore reads from it, and while storage cleanup fails. The `backup.keeper.dev/skip-storage-cleanup=true` annotation is the escape hatch. — Deleting data that a restore is using is a correctness bug. Silently leaking objects is a cost bug. — If it's wrong: a Backup can hang in Terminating until the annotation is set.
- Ruling: a Restore never overwrites existing claims. It creates `<prefix><source>` claims in the Backup's namespace, and a pre-existing claim fails it with `TargetExists`. — In-place restore of a live claim is how data gets destroyed. — If it's wrong: users repoint workloads at the restored claims by hand.
- Ruling: a CSI Restore counts as complete once its claim exists. — With WaitForFirstConsumer storage classes, binding happens only when a pod uses the claim. — If it's wrong: a provisioning failure shows up on the PVC, not on the Restore.
- Ruling: events use the `events.k8s.io/v1` recorder (`mgr.GetEventRecorder`). — The core/v1 recorder is deprecated in controller-runtime v0.25. — If it's wrong: nothing. Note that client-go rate-limits events per object, so event counts can trail the metrics (seen in the demo: 222 Pruned events vs 227 pruned).

## Testing and tooling

- Ruling: envtest (a real kube-apiserver and etcd, v1.37.0) backs the integration tests and the demo. envtest has no kubelet, snapshot controller or provisioner, so `internal/simcluster` plays those parts. It runs mover Jobs in-process with the real mover code against local directories, and cuts snapshots by copying directories. — This gives real API semantics (CEL, status subresources, finalizers, field indexes, Job status validation) without a cluster or Docker. — If it's wrong: the Job pod spec (image, security context, secret env) is asserted but never executed by a real kubelet. See Limitations.
- Ruling: the envtest binaries are downloaded once by `setup-envtest` into its standard per-user cache and reused offline afterwards. `make check` sets `KEEPER_REQUIRE_ENVTEST=1`, so the integration tests can't skip silently. — The contract says checks must not need the network. Vendoring roughly 100 MB of binaries into the repo is worse. — If it's wrong: the first `make check` on a new machine needs network access, as `go mod download` does.
- Ruling: the S3 client is minio-go v7. Unit tests run it against an in-process fake S3 (`internal/storage/s3test`) that handles aws-chunked bodies and multipart uploads. `make integration` runs the same conformance suite against a real MinIO in Docker. — The fake keeps `make check` hermetic, and the Docker run is what checks real SigV4 signing. — If it's wrong: the fake does not verify signatures. MinIO does.
- Ruling: the MinIO image for `make integration` is `chainguard/minio` pinned by digest. — `minio/minio` on Docker Hub refused pulls in this environment, and the quay.io copy needed authentication. — If it's wrong: the digest may be garbage-collected upstream someday. Override it with `MINIO_IMAGE=...`.
- Ruling: the coverage gate (80%) applies to the operator's own packages. Test infrastructure (simcluster, fake S3, conformance suite) and the declarations-only metrics package are left out (`hack/coverage.sh`). — Coverage of test helpers says nothing about product quality. — If it's wrong: the number is not comparable to a whole-module figure. The script prints every package.
- Ruling (fix round 1): finalize runs post hooks for a Backup deleted in PreHooks, Snapshotting or PostHooks, then persists `Failed`/`DeletedInProgress` before cleanup. — Review found two ways to leave an application frozen: deletion between the Snapshotting→PostHooks write and the post-hook reconcile, and a deletion whose resourceVersion bump made the PreHooks→Snapshotting write conflict after the freeze had run. Persisting a terminal phase keeps a blocked deletion (running Restore, storage outage) from re-thawing on every requeue. — If it's wrong: a Backup deleted in PreHooks before its freeze ran gets one thaw with no freeze, which the existing ruling already requires post hooks to tolerate.
